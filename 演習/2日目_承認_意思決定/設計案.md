# 差し戻された申請を出し直したときの戻り先 - 設計案

## 決めたいこと

差し戻された申請を申請者が出し直したとき、申請はどの役割の承認待ちになるか。変更仕様書の中で次の 2 つが食い違っている。

- 状態遷移の表: 決裁権限表の最初の承認者の承認待ち
- 承認一覧の画面の記述: 差し戻した段階の承認者の承認待ち

spec の現状は次のとおり。

- requirements.md の未決定に置いてあり、5.1 と 5.4 は戻り先を書いていない
- design.md の `purchase_request` は、`status = PENDING` のときだけ `pending_role` を持つ(CHECK 制約)。差し戻し中の申請は、どの段階で差し戻されたかを持たない
- 5.4 により、出し直しでは金額と明細を変えない
- 履歴 `approval_history` に役割の列はなく、差し戻した段階は履歴からも求められない
- 出し直しは申請者本人だけが行い、代理は不可(7.7)

以下の例では、担当者が 150,000 円を申請する。承認者の並びは 課長 → 部長 とする。課長が承認し、部長が差し戻したとする。

## 案 1: 常に最初の承認者からやり直す

### どう動くか

- 出し直したとき、`ApprovalPolicy.route(申請者の役割, 申請金額)` の先頭の役割を `pending_role` にする
- 例では課長の承認待ちに戻る。課長が承認し、部長が承認して、承認済みになる
- テーブルの変更はない。`resubmit` は `route(...).get(0)` を `pending_role` に入れるだけである
- 履歴には、課長の最初の承認、部長の差し戻し、出し直し、課長の 2 回目の承認が残る

### 良い点

- 状態遷移の表(requirements.md の 業務の決まり)と一致する
- 実装が最も小さい。新しい列も、新しいエラーも要らない
- 決裁権限表の並びの全員が、必ず承認する。承認者が部署や役割の変更で入れ替わっていても、途中の承認者が抜けない
- 差し戻しの後に申請者が何を直したかを、下位の承認者も確かめられる

### 悪い点

- 部長が見積書の不足を指摘しただけでも、課長が同じ申請をもう一度承認する。課長の手間が増える
- 承認の段数が多い申請(100 万円超は 3 段)ほど、役員の差し戻しの後の手戻りが大きい
- 承認一覧の画面の記述(差し戻した段階に戻る)と食い違うため、画面の記述を直す必要がある

### 前提にしていて崩れやすいこと

- 出し直しの前後で、申請の内容が承認の判断に影響するほど変わりうる、という前提に立っている。5.4 のとおり金額と明細を変えられないなら、この前提は弱い。内容が変わらないのに課長がもう一度承認する意味を、利用者が見いだせないと、不満が出る
- 課長が前回承認した事実を、もう一度承認させる理由として扱っていない。前回の承認を有効とみなしたい要望が出ると、この案は作り直しになる

## 案 2: 差し戻した段階の承認者から再開する

### どう動くか

- 差し戻すときに、そのときの `pending_role` を申請に保存する。出し直したとき、保存した役割を `pending_role` に戻す
- 例では部長の承認待ちに戻る。課長の最初の承認は有効のままで、部長が承認して承認済みになる
- 保存先は `purchase_request` に足す列 `returned_from_role`(`status = RETURNED` のときだけ値がある)とする。CHECK 制約は `(status = 'RETURNED') = (returned_from_role IS NOT NULL)` を足す
- 出し直しの条件付き UPDATE は、`status = RETURNED` と `returned_from_role` が読んだ値と同じ、を条件に加える

### 良い点

- 承認一覧の画面の記述と一致する
- 差し戻した承認者だけが、直った申請を確かめる。下位の承認者の手間が増えない
- 5.4 のとおり内容が変わらない出し直しと、整合する

### 悪い点

- テーブルを 1 列足し、不変条件と CHECK 制約を増やす。design.md の 状態遷移は表と同じ という書き方も直す必要がある
- 状態遷移の表(最初の承認者の承認待ち)と食い違うため、表を直す必要がある
- 課長が承認した後に申請が部長へ進み、差し戻されて戻る間に、課長の承認がまだ成り立つかを確かめる仕組みがない。課長の承認が代理人によるもので、代理期間が終わっていても、その承認は残る
- 差し戻した承認者が、代理人だった場合の扱いを決める必要がある。戻り先の役割は代理元の役割にするが、代理期間が出し直しの前に終わっていると、代理人は承認できない。承認できるのは代理元本人だけになる

### 前提にしていて崩れやすいこと

- 差し戻される前の段階の承認が、出し直しの後も有効であるという前提に立っている。申請の内容が変わらない(5.4)間は成り立つ。後で出し直しの時に明細を直せるようにすると、金額の帯が変わりうるため、前の承認者の承認が無効になる。そのときは案 1 か案 3 の考え方が必要になる
- 承認者の並びが、差し戻しの間に変わらないという前提に立っている。社員の役割や部署が変わった場合に、保存した役割が並びに無い可能性がある。`route` に含まれない役割が保存されていないかを、出し直しのときに確かめる処理が要る

## 案 3: 差し戻す承認者が、戻り先を選ぶ

### どう動くか

- 差し戻すときに、理由に加えて戻り先を指定する。戻り先は、`route` の中で差し戻した段階以前の役割から選ぶ。指定がなければ案 1(最初)とする
- 例では、部長が課長の再確認を要すると判断すれば課長へ、部長の確認だけで足りると判断すれば部長へ戻せる
- API は `POST /api/approval/requests/{id}/return` の本文に `returnTo`(役割)を足す。`purchase_request` に、案 2 と同じ列 `returned_to_role` を足し、出し直しのときにそのまま `pending_role` に入れる
- 戻り先が `route` の中で差し戻した段階より後ろ、または並びに無い役割のときは、A01・A02・A03 のどれにも当てはまらない。新しいエラーコードが必要になる

### 良い点

- 食い違っている 2 つの記述を、どちらも選べる。状況に応じて、承認者が決められる
- 業務の実態に近い。見積書が足りないだけなら差し戻した段階に戻し、内容の判断を覆すなら最初に戻せる

### 悪い点

- 3 案の中で最も実装が大きい。API の本文、列、検証、エラーコード、画面の選択肢が増える
- 戻り先の検証を、複数の原因が重なるときのエラーの優先順位(未決定)に加える必要がある
- 承認者の判断が人によって変わる。同じ状況でも、承認者ごとに戻り先が違うと、利用者が結果を予測できない
- 変更仕様書のどちらの記述にも無い機能を足す。仕様書の食い違いを、仕様書にない機能で解消することになる

### 前提にしていて崩れやすいこと

- 承認者が、戻り先を選べるだけの情報と責任を持っているという前提に立っている。迷ったときの既定が案 1 になるなら、案 3 は案 1 と変わらない
- 戻り先を選べる範囲を、差し戻した段階以前に限ると、役員が差し戻す場合は、戻り先に課長・部長・役員のどれも選べる。選べる範囲を絞りたい要望が出ると、検証が複雑になる
- エラーコードを 3 つに保てるという前提(requirements.md の エラーは次の 3 つとする)を崩す。新しいコードを足すか、A02 の意味を広げるかを決める必要がある

## 比較

| 観点 | 案 1 最初から | 案 2 差し戻した段階から | 案 3 差し戻す人が選ぶ |
|---|---|---|---|
| 状態遷移の表との一致 | 一致する | 食い違う(表を直す) | 既定は一致する |
| 承認一覧の画面の記述との一致 | 食い違う(記述を直す) | 一致する | 選んだ場合に一致する |
| テーブルの変更 | なし | 1 列と CHECK 制約 | 1 列と CHECK 制約 |
| API の変更 | なし | なし | `return` の本文に戻り先を足す |
| エラーコードの追加 | なし | なし | 要る |
| 5.1 と 5.4 の書き方 | 戻り先を書ける | 戻り先を書ける | 戻り先は差し戻し時の指定と書く |
| 承認者の手間 | 下位の承認者の手間が増える | 増えない | 承認者の判断による |

## 決めるときの確認事項

案を選ぶ前に、次の 3 点を変更仕様書の作成者に確かめる必要がある。

1. 出し直しのときに、明細と金額を直せるようにするか。5.4 は直さない前提である。直せるなら、案 2 の前提が崩れる
2. 前回の承認は、出し直しの後も有効とみなしてよいか。有効とみなせないなら、案 2 は使えない
3. 差し戻しの理由が、内容の誤りか書類の不足かで、扱いを分ける業務上の根拠があるか。無いなら、案 3 の選択肢は使われない
